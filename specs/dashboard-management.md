# Managed dashboard lifecycle

Status: Normative  
Scope: Target discovery, template rendering, Home Assistant websocket operations, resources, ownership, localization, pruning, and diagnostics

## Defaults and prerequisites

- **REQ-DASH-001** — Defaults are asset directory `/opt/gosungrow/assets`, Home Assistant config `/homeassistant`, websocket `ws://supervisor/core/websocket`, URL path `gosungrow-flow`, title `GoSungrow Flow`, icon `mdi:solar-power`, visible in sidebar, non-admin-readable, language `auto`, and no force update.
- **REQ-DASH-002** — Initial installation requires `SUPERVISOR_TOKEN` and a forced valid iSolarCloud login. Failure to authenticate, discover any valid target, load assets, authenticate Home Assistant, or save required managed state MUST fail the dashboard command. Availability-driven reconciliation under REQ-DASH-039 MUST use already discovered target information and MUST NOT force another iSolarCloud login solely because an HA entity changed; initial installation and independent API-session recovery retain their existing authentication requirements. When REQ-API-037 activates the inventory fallback, the installer MUST satisfy the complete target requirement in REQ-DASH-043 before mutating dashboard resources, configuration, or persisted state.

## Target discovery

- **REQ-DASH-003** — Plants MUST be processed by sorted opaque `ps_id`. Devices without `ps_key` are ignored.
- **REQ-DASH-004** — Every type-14 device in a plant is a dashboard target. If none exists, select exactly one fallback ranked `11`, `7`, `1`, then other; ties preserve deterministic discovery order.
- **REQ-DASH-005** — Target selection source MUST identify the chosen device type. All usable plant devices and which one is selected MUST be retained for diagnostics and semantic matching.
- **REQ-DASH-006** — A target title is the normalized plant name; use `Plant <ps_id>` if absent. With multiple targets in a plant, append distinct device name or key. If titles still collide, append `ps_id`.
- **REQ-DASH-007** — View paths MUST lowercase, convert `_` to `-`, replace non-alphanumerics with `-`, trim separators, and fall back to `gosungrow-flow`.
- **REQ-DASH-043** — When any in-scope plant uses the inventory fallback, every in-scope plant MUST have at least one verified selected target before the dashboard can be saved. If coverage is incomplete, fail the standalone installation with reason `target_coverage_incomplete` and leave existing dashboard configuration, resources, and state untouched. Runtime discovery MUST retain the last complete target set and MUST NOT save from the incomplete refresh. When no complete set exists, defer dashboard creation. The app MUST continue MQTT under REQ-ADDON-004. Runtime reconciliation MUST reuse the complete discovery result under REQ-DASH-039. An HA eligibility event MUST NOT start a new cloud discovery or login solely because the event occurred. With complete coverage, apply the identity guard under REQ-DASH-046 before writing.
- **REQ-DASH-044** — Apply REQ-DASH-003–006 to verified inventory. Select all type-14 devices and order them lexically by opaque `ps_key`. If no type-14 device qualifies, use the existing `11`, `7`, `1`, then other ranking. Among tied inventory candidates, keep an existing managed target if it is still eligible at the best rank. Otherwise select the lexically smallest tied `ps_key`. For a managed dashboard affected by fallback, preserve its existing target keys, view titles and paths, mapping identities, pinned defaults, and accepted overrides while the targets remain eligible. If inventory would add, remove, or replace an existing target, or the existing views cannot be uniquely attributed to the verified targets, defer the write until a complete tree-based refresh can verify the change. Existing ownership and verified-save requirements continue to apply. On tree recovery, keep the existing equally ranked target and preserve titles and paths for the same verified target set. A complete tree-based refresh that establishes a genuinely different eligible target set follows the normal reconciliation rules.
- **REQ-DASH-046** — The identity guard applies to dashboard attempts that use inventory fallback and to tree recovery for a previously recorded `inventory_target_plants` entry in scope. Once coverage is verified, check every selected target and rendered view, including targets from healthy trees. An identity conflict exists if two views would share a final path after applying any preserved paths, two distinct `(ps_id, ps_key)` pairs generate the same mapping ID under REQ-SRC-001, or distinct selected `ps_key` strings compare equal under Unicode simple case folding after trimming. Reusing a saved identity for the same verified target is valid. Missing coverage takes precedence over an identity conflict. A confirmed conflict takes precedence over unverified continuity. When continuity cannot be established and no conflict is confirmed, use `target_continuity_unverified`.

  On conflict, standalone installation MUST fail with reason `target_identity_conflict`. Runtime MUST defer the write, retain the last complete target set when available, and continue MQTT under REQ-ADDON-004. Check before any dashboard, resource, asset, or dashboard-state mutation, including on a fresh install. The attempt MUST NOT drop targets, synthesize replacement paths or mapping IDs, reassign saved source selections, or advance the saved inventory marker.

## Template and layout

- **REQ-DASH-008** — The bundled YAML MUST contain prototype views `Overview`, `Aggregates`, `Trends`, and panel view `Data Sources`, in that order, containing the metric set from [domain-model.md](domain-model.md).
- **REQ-DASH-009** — Every prototype MUST be cloned for every target and every `YOUR_ESS_PS_KEY` occurrence recursively replaced. With multiple targets, titles and paths combine target and prototype; with one target, prototype titles/paths remain.
- **REQ-DASH-010** — Overview MUST show live flow, today tiles, 24-hour power balance, battery state, and daily energy. Trends MUST show power balance, solar allocation, load sources, grid exchange, battery flow/SOC, and daily energy. Aggregates MUST show day/month/year summaries for production, consumption, grid directions, and battery directions.
- **REQ-DASH-011** — Unsupported target-specific metrics MUST be pruned from entity maps/lists and display cards; empty non-heading cards and sections containing only headings MUST be removed. Unsupported decisions MUST use the final resolution under REQ-RES-022, after canonical matching and consideration of saved selections. A confident canonical source MUST NOT be pruned because legacy name matching failed or its entity was renamed. A preserved daily selection MUST retain its identity and actionable Data Sources review entry even when its numeric presentation is withheld under REQ-SRC-029; preservation MUST NOT make an otherwise forbidden value displayable. Pruning MUST remain per target and MUST NOT run when Home Assistant states are unavailable. Binding construction MUST preserve metric identity and use positions in the final dashboard configuration.
- **REQ-DASH-012** — Battery capability requires a usable numeric, target-affine SOC entity with unit `%`/empty or battery-power entity with power unit/empty. Battery energy alone does not establish capability.
- **REQ-DASH-013** — Battery metrics remain `battery_power`, `p13141`, `p13174`, `p13029`, `pv_to_battery_power`, and `battery_to_load_power`. A canonical daily metric is unsupported when it has neither a confident eligible canonical source nor a saved selection requiring preservation under REQ-SRC-005, 013, or 014. A preserved metric's display permission MUST be evaluated separately under REQ-SRC-028–030. Canonical plant PV MUST use the shared composition outcome and saved-source protections under REQ-RES-022 and REQ-SRC-026. Other unresolved metrics remain unsupported. Battery capability remains governed by REQ-DASH-012.

## Localization

- **REQ-DASH-014** — Supported locales are `en`, `de`, `sv`, and `es`; locale files MUST have identical key sets for dashboard and app option translations.
- **REQ-DASH-015** — `auto` MUST query Home Assistant user frontend data first and core config second. Language normalization lowercases and changes `_` to `-`; lookup order is full locale, base language, then English.
- **REQ-DASH-016** — Missing locale/key or blank translation MUST fall back to English. Exact known template strings are localized recursively, and flow-card labels are injected into every flow card.

## Asset and websocket contract

- **REQ-DASH-017** — The installer MUST calculate the bundled card's full SHA-256 hash and atomically stage identical bytes under every writable unique candidate config root (configured directory, `/homeassistant`, `/config`) at `www/gosungrow/gosungrow-dashboard-cards.<sha12>.js`, where `<sha12>` is the first 12 lowercase hexadecimal hash characters. Every successful write MUST be re-read and match the full hash, and at least one canonical write MUST succeed.
- **REQ-DASH-018** — The registered JavaScript resource MUST have type `module` and canonical URL `/local/gosungrow/gosungrow-dashboard-cards.<sha12>.js`. Before activation, a request to Home Assistant's separately resolved static HTTP origin for that exact path MUST return status 200, a JavaScript MIME type, and bytes matching the full expected hash. Newly registered data URLs, mutable local URLs, and CDN URLs are prohibited.
- **REQ-DASH-019** — Legacy GoSungrow data URLs, CDN URLs, unversioned local URLs, and content-addressed local URLs MUST all be recognized as managed resources and migrated to exactly one canonical resource without duplicating it or changing unrelated resources. After successful activation, each candidate root MUST retain the active and immediately previous verified content-addressed bundles and remove only older unreferenced managed bundles.
- **REQ-DASH-020** — Websocket connection uses bearer token, 15-second handshake/write timeout, 30-second reads, monotonically increasing request IDs, and ignores unrelated response messages until the matching result arrives.
- **REQ-DASH-021** — Supported Home Assistant operations are dashboard list/create/update/delete, Lovelace config read/save, resource list/create/update/delete, states, entity registry, relevant state/registry change observation, and preferred-language calls. Observation MUST support cancellation and a fresh state/registry snapshot after reconnection. Structured websocket error code/message MUST be preserved.
- **REQ-DASH-022** — State list MUST discard empty IDs and deduplicate case-insensitively. Registry metadata MUST enrich matching states by case-insensitive entity ID; registry failure degrades to conservative fallback instead of aborting install.

## Ownership and persistence

- **REQ-DASH-023** — State file is `dashboard_state.json` beside `GOSUNGROW_CONFIG`, or the OS temporary directory when that variable is absent; it stores URL path, full config hash, structure hash, target keys, accepted overrides, asset mode (`enhanced` or `native-fallback`), active asset URL and full hash, previous asset URL and full hash, and UTC update timestamp with mode `0600`. Legacy state without asset fields MUST remain readable and MUST be migrated on the next successful reconciliation. Persist an optional `inventory_target_plants` array in existing dashboard state. It contains sorted, distinct opaque plant IDs whose successfully saved targets were established or verified through inventory fallback. Maintain an entry while that plant remains in the managed dashboard so REQ-DASH-044 applies across restarts and tree recovery. Interpret an absent field as an empty array. Persist this metadata only after verified dashboard save or verified unchanged reconciliation.
- **REQ-DASH-024** — Canonical JSON hashing MUST preserve array order, sort object keys, encode primitives as JSON, and use full SHA-256 hex.
- **REQ-DASH-025** — A dashboard is managed only when persisted state names the same URL path. A non-storage dashboard at the path MUST be rejected.
- **REQ-DASH-026** — An unmanaged existing dashboard or an externally modified managed dashboard MUST be rejected unless force update is true.
- **REQ-DASH-027** — Source-only changes are not external structural modification. Structure hashing MUST replace valid bound source paths with stable metric placeholders and remove source defaults, overrides, bindings, candidates, recommendations, matcher/validation version, selection origin, semantic verification, display decision, source-policy reasons, and live/source status fields. The same normalization MUST apply to recognized `source_policy` metadata attached to display cards under REQ-SRC-031 and `gosungrow_source_mapping` metadata retained under REQ-DASH-042, so policy migration or source-only metadata changes are not mistaken for unrelated user layout modification. For REQ-SRC-032's native projections, ownership comparison MUST validate template/path ownership, normalize valid template entity references by their canonical metric, and account for expected source-policy filtering/restoration without dropping the template's non-source structural evidence. Unrelated edits to either the template's non-source configuration or the rendered layout MUST remain detectable; removing policy metadata MUST NOT hide those edits. Template-relative paths MUST NOT be applied as rendered-dashboard paths. This normalization MUST NOT hide unrelated layout edits or treat retained obsolete binding paths as valid paths in the current configuration.
- **REQ-DASH-028** — Legacy state without a structure hash MAY be accepted only when normalized current and desired structures match. Config is saved only when new, changed, or forced; metadata is updated/created independently. Availability-driven reconciliation MUST NOT save an unchanged desired dashboard even when the configured force flag permits replacement; force permission does not require a redundant write.

## Diagnostics

- **REQ-DASH-029** — Installation MUST report context, state-load result, GoSungrow-state count, reference/remap/unresolved counts, battery detection, save decision/reason, targets and selection, relevant warnings, and unresolved references.
- **REQ-DASH-045** — If a tree denial affects a dashboard discovery attempt or the identity guard detects a conflict on tree recovery, emit one bounded normal-log summary beginning `Dashboard target discovery:`. Include `app_version`, `source` (`tree`, `device_list`, `mixed`, or `none`, based on verified targets), `requested_plants`, `verified_plants`, `verified_targets`, and `decision` (`complete` or `deferred`). Include `reason=none` for complete discovery. For a deferred attempt, use `reason=target_coverage_incomplete` for missing or unverifiable targets, `reason=target_identity_conflict` for a conflict under REQ-DASH-046, or `reason=target_continuity_unverified` when the managed target or view continuity rules defer a write. Report the save outcome separately under REQ-DASH-029. Exclude plant and device identifiers, credentials, tokens, headers, and payloads from the summary. Keep a separate denial record for each observed HTTP 403 under the existing diagnostic rules.
- **REQ-DASH-030** — Debug mode additionally reports bounded candidate traces. Diagnostics MAY include entity IDs/current values but MUST exclude credentials and tokens.
- **REQ-DASH-031** — Enhanced dashboard delivery MUST be one transaction: build the complete desired dashboard and verify ownership before mutation; stage and hash the asset; verify its Home Assistant HTTP response; create or update the managed resource; re-read and verify its exact URL and type; save and re-read the dashboard; then persist local state. If any step after resource mutation fails, the installer MUST restore the prior managed resource registration and dashboard configuration. A failed upgrade of an existing working installation MUST leave its prior resource, dashboard, and state usable.
- **REQ-DASH-032** — On a fresh installation where custom-card activation fails but Home Assistant dashboard storage remains available, the installer MUST save a native fallback rather than custom-card references. The fallback MUST preserve targets and view paths, present permitted resolved live metrics in canonical domain order through native cards, present permitted current-period summary entities through native cards, replace source mapping with a localized informational card that editing may be unavailable, and contain no `custom:gosungrow-*` type. The native Data Sources notice MUST retain non-rendered source-selection metadata under REQ-DASH-042. It MUST apply REQ-SRC-029 and REQ-CARD-021: withheld daily values are replaced by an actionable review/unavailable explanation, and displayed unverified manual values carry persistent warnings. Later reconciliation MUST automatically promote the dashboard to enhanced mode without losing target or source-selection decisions.

- **REQ-DASH-042** — A native Data Sources notice MUST retain a non-rendered `gosungrow_source_mapping` object for its target. Its fields MUST be `schema_version`, `matcher_version`, `mapping_id`, `dashboard_url_path`, `defaults`, `pinned_defaults`, `overrides`, and `metrics`. Schema and matcher versions MUST identify the source-mapping contract being retained under REQ-SRC-001; target and dashboard identities MUST remain isolated. `metrics` MUST retain each canonical metric's existing `key` and the selection/policy fields `entity_id`, `selection_origin`, `verification`, `display_decision`, and `reason` from REQ-SRC-031. The object MUST NOT retain transient candidates, obsolete rendered-dashboard binding paths, live availability, numeric measurement values, credentials, or raw payloads. Restorable per-card presentation metadata, where needed, MUST remain on the affected native display card under `source_policy.native_template` and `source_policy.native_bindings` as specified in REQ-SRC-032; those valid template-relative paths are distinct from obsolete dashboard positions and MUST NOT be copied into the notice as active bindings. Promotion back to enhanced mode MUST preserve saved defaults, pinned defaults, and accepted override identities while rebuilding verification, candidate lists, display decisions, and final binding paths from fresh observations. Retained metadata MUST NOT authorize numeric presentation or imply current source eligibility; current configuration/reset precedence remains governed by REQ-SRC-016. Fallback retention and promotion MUST preserve REQ-DASH-027's ownership protections and MUST NOT introduce a custom fallback card, new state file, or service, mutate recorder history, or overwrite unrelated layout.
- **REQ-DASH-033** — After the first managed-resource registration or a managed-resource URL replacement, the installer MUST use Home Assistant's storage-resource mutation and re-read path so new browser sessions receive the new URL. Successful read-back of the exact canonical resource URL and `module` type completes the resource step. GoSungrow MUST NOT call `lovelace.reload_resources` during managed installation or reconciliation, even when Home Assistant advertises it. A browser opened before registration MAY require one ordinary reload; content-addressed URLs MUST make a hard refresh unnecessary. The installer MUST NOT forcibly navigate or reload connected browsers.
- **REQ-DASH-034** — Asset lifecycle diagnostics MUST use bounded structured fields covering phase, expected hash, canonical URL, HTTP verification route (`supervisor-core-info` or `websocket-origin`), Supervisor metadata HTTP status and outcome, discovered Core port and TLS setting, asset HTTP status and MIME type, static-route outcome, required operator action, resource action, dashboard mode, rollback result, and cleanup result. They MUST NOT print HTTP origin URLs, IP addresses, Supervisor metadata response bodies, JavaScript bodies, base64-encoded assets, credentials, or tokens.
- **REQ-DASH-035** — Static asset verification MUST resolve transport independently from the Home Assistant API websocket. When the normalized websocket hostname is `supervisor` and its path ends in `/core/websocket`, before every installation or reconciliation verification it MUST request `http://supervisor/core/info` with `Accept: application/json`, the `SUPERVISOR_TOKEN` as a bearer credential, a 15-second request bound, and redirects disabled. The response MUST have HTTP status 200 and a JSON envelope with `result` exactly `ok`, `data.port` as an integer from 1 through 65535, and `data.ssl` as a boolean; unknown fields MUST be ignored. The verifier MUST use scheme `https` when `data.ssl` is true and `http` otherwise, hostname `homeassistant`, and the exact advertised port. It MUST NOT assume port 80 or 8123, probe ports, silently fall back when discovery is unavailable or invalid, persist or reuse discovered topology across reconciliations, or disable standard TLS certificate verification. Otherwise it MUST map `ws` to `http` and `wss` to `https`, remove a terminal `/api/websocket` or `/websocket` while preserving any preceding base path, and use the resulting origin. The verifier MUST append the canonical resource path without changing it, MUST NOT request `/core/local/...` through Supervisor, MUST attach the Supervisor credential only to `/core/info` and no credential to the static request, and MUST NOT follow redirects.
- **REQ-DASH-036** — Supervisor endpoint-discovery failure and static asset verification failure MUST remain custom-card activation failures governed by `REQ-DASH-031` and `REQ-DASH-032`: an existing working dashboard remains usable, a fresh installation receives the native fallback, and MQTT startup continues. Diagnostics and returned error chains MUST distinguish Supervisor metadata discovery from the subsequent static asset fetch while preserving a safe causal error. The `/local` HTTP 404 bootstrap case defined by `REQ-DASH-037` is locally recoverable and MUST NOT be classified as non-recoverable.
- **REQ-DASH-037** — When the exact staged asset has been written, re-read, and hash-verified but Home Assistant returns HTTP 404 for its canonical `/local/...` URL, the installer MUST classify the condition as static-route outcome `home-assistant-static-route-unavailable` with stable failure class `operator_action_required`. It MUST tell the user to restart Home Assistant Core once, state that restarting the GoSungrow app is insufficient, and state that GoSungrow reconciliation will retry automatically. It MUST NOT restart Core automatically, register the unverified resource, or apply this classification or guidance to another HTTP status, MIME failure, hash failure, transport failure, or Supervisor-metadata failure. An existing working dashboard MUST remain unchanged; a fresh installation MUST receive the native fallback. After Core restarts, the next reconciliation MUST rediscover transport, verify the asset, activate enhanced mode, and clear the condition without losing targets or source-selection decisions. Because registration occurs only after successful HTTP verification, a browser MUST NOT be directed to the unavailable content-addressed URL during this failure state.

- **REQ-DASH-038** — Debug diagnostics for canonical daily metrics and canonical plant PV MUST describe the final composition outcome, including target key, metric, selected and effective display entity or absence, whether the source is canonical, pinned, manual, or unavailable, semantic verification, display decision, confidence, eligible-candidate count, final reason, and binding count. Candidate detail MUST remain bounded to five entries per metric and distinguish eligible and rejected sources with reasons. Diagnostics MUST distinguish missing eligible candidates, ambiguous candidates, unavailable canonical registry verification, preserved unverified selections, and proven incompatibility. They MUST exclude credentials and tokens and MUST NOT present a discarded legacy match or withheld selection as the effective displayed measurement.

## Availability-driven reconciliation

- **REQ-DASH-039** — While managed dashboard installation is enabled, relevant HA entity/registry availability or eligibility changes MUST remain observable after the startup reconciliation schedule ends. Creation, removal, identity changes, or state/freshness changes that alter a target metric's eligibility MUST trigger reconsideration; ordinary numeric updates that do not change eligibility MUST NOT trigger reconciliation. Relevant changes MUST be coalesced within a fixed five-second window starting with the first change, rather than extending the window on every update. Scheduled and availability-driven reconciliation MUST be serialized with at most one pending follow-up. Each run MUST use a fresh HA state/registry snapshot and the shared final composition result, preserving accepted manual selections and offering safer sources for pinned selections under REQ-SRC-007 and REQ-SRC-026. Observation and reconciliation MUST NOT change MQTT entities or bypass ownership, force permissions, or verified dashboard-save transactions.
- **REQ-DASH-040** — A transient availability-driven reconciliation failure MUST allow at most three retries after sequential delays of 30, 90, and 300 seconds; after exhaustion it MUST wait for a new relevant transition or explicit reconciliation. Changes and scheduled attempts arriving during a run or retry wait MUST coalesce rather than create parallel attempts. A failed observer connection MUST reconnect after sequential delays of 30, 90, and 300 seconds, then at most once per 300 seconds while enabled. Reconnection MUST refresh state/registry observations to recover missed transitions; reconnecting alone with unchanged eligibility MUST NOT regenerate or save a dashboard. Non-recoverable conditions MUST retain their actionable classification rather than enter a transient reconciliation retry loop. Observer and reconciliation failures MUST remain nonfatal to MQTT, MUST NOT trigger API authentication recovery solely because observation failed, and MUST be cancelled when the main runtime exits. Availability-driven reconciliation MUST NOT save unchanged desired configuration under REQ-DASH-028.

## Correlated source diagnostics

- **REQ-DASH-041** — Existing debug logs MUST provide a bounded source-diagnostic capture spanning a sync and reconciliation without a new service, diagnostic UI, public endpoint, or HTTP tracing. Records MUST identify app and matcher versions, UTC observation time, plant, target, metric, applicable sync/reconciliation identifier, and stage. HA observation MUST report registry availability, the canonical discovery identity being sought, the matching actual entity ID or not-observed result, numeric validity, unit, update time, and freshness. Composition MUST report saved selection origin, verification, eligible/rejected candidates and reasons, recommendation, display decision, binding count, and save outcome. These records MUST correlate with publication evidence under REQ-MQTT-023 and REQ-MQTT-026 through stable plant/measurement identities and explicit observation times, without asserting that separate observations are one atomic snapshot. Missing or failed observations MUST remain explicit; no observed candidate is not proof that the API supplies no such measurement. Candidate detail MUST obey the five-per-metric limit, normalized-point detail MUST obey REQ-MQTT-026, and all capture records MUST obey REQ-XCUT-023. Diagnostics MUST distinguish publisher completion, HA entity observation, and dashboard binding; none proves browser display or arithmetic correctness.

## Prohibited behavior

- Cross-plant source assignment on multi-target dashboards.
- Treating a missing manual entity as permission to choose a replacement.
- Overwriting user structure without force permission.
- Saving `custom:gosungrow-*` references before their exact resource has been verified and activated.
- Deleting the last verified working managed bundle or changing unrelated Lovelace resources.
