# Acceptance scenarios

Status: Normative  
Scope: Cross-subsystem executable examples

## Authentication and transport

- **REQ-ACC-001** — Given a missing token file, login proceeds to the network without a file error; given corrupt token JSON, the file is removed and login proceeds.
- **REQ-ACC-002** — Given configured host/key rejection, login tries unique candidates in specified order. The Indian gateway occurs exactly once in automatic rotation; when configured explicitly it is first, while the existing gateways retain their relative order. Given `127.0.0.11:53` on the first candidate, rotation stops and returns for DNS backoff. Given an earlier authentication/gateway failure followed by `127.0.0.11:53` on a later candidate, rotation stops, preserves both failures, and remains classified as a recoverable remote login sequence rather than a general Docker-DNS outage.
- **REQ-ACC-003** — Given a timed-out HTTP request, a later request can succeed because requests use a bounded private client rather than corrupting the global client.
- **REQ-ACC-004** — Given a common request with a token, debug string contains `<redacted>` and not the token.

## Data

- **REQ-ACC-005** — Numeric and composite plant IDs round-trip; `NULL`, `--`, and invalid composite placeholders do not become zero.
- **REQ-ACC-006** — Given kVAr/MVAr/mVAr variants, reactive power publishes equivalent `var` values and `reactive_power` metadata; applying normalization twice changes nothing.
- **REQ-ACC-007** — Given any missing operand in a virtual formula, dependent virtual points are absent while independent virtual points remain.
- **REQ-ACC-008** — Given a plant-local timestamp, its wall-clock components remain and correct zone offset is attached; invalid timezone retains the original.

## MQTT and Home Assistant

- **REQ-ACC-009** — Given one plant with types 14, 11, and 22, realtime selects type 14; without 14 it selects 11; each additional plant gets its own batch.
- **REQ-ACC-010** — Given Docker DNS loss after connection, MQTT remains connected and delays follow 15/30/60/120/300 seconds; success restores five minutes.
- **REQ-ACC-011** — Given textual, numeric instant, numeric daily, and reactive-power values, discovery respectively has no measurement metadata, measurement, total/last-reset, and canonical reactive metadata. Given a valid text reading such as `offline` with source unit `W/㎡` or `Wh/㎡`, discovery MUST omit the unit, state class, and last-reset metadata.
- **REQ-ACC-030** — Given a numeric `Wp` value, normalization and discovery publish the scaled value in `kWp` with frequency-derived state metadata and `mdi:lightning-bolt`, but without `device_class`; given an otherwise equivalent `kW` value, discovery continues to publish device class `power`.
- **REQ-ACC-031** — Given two producer leaves reporting `1.2 kW` and `800 W` DC with no native total or complete AC tier, the plant publishes `2.000 kW` at `sensor.gosungrow_virtual_<ps_id>_pv_power`. A valid native plant total wins without adding device values; complete AC coverage wins over DC coverage; topology excludes a parent when its children contribute. Mixed incomplete AC/DC coverage, a missing expected contributor, an invalid value, or an incompatible unit produces no new aggregate. A new dashboard selects the plant entity, an existing pinned or manual source is not silently rewritten, and without an aggregate multiple producers cannot resolve to one automatic plant total.
- **REQ-ACC-032** — Given plant-tree UUID/UpUUID relationships and expected producers established independently from current numeric values, producer leaves are resolved within their opaque plant ID, including relationships through intermediate non-producing nodes. Duplicate UUIDs, dangling or cross-plant parent references, parent cycles, and unavailable topology suppress device aggregation without stopping MQTT; a native plant total still publishes. Successful token recovery refreshes device inventory, discovered point metadata, and plant topology; unsuccessful rediscovery does not redefine expected producer membership.
- **REQ-ACC-076** — Given an instant reading of `21.5` in each of the six input unit spellings in REQ-HA-021, the normal MQTT publication path MUST publish the corresponding canonical unit, the `temperature` device class, the `measurement` state class, and the unchanged numeric reading. Given an existing sensor with retained discovery using `℃`, the next discovery refresh MUST publish `°C` on the same config topic with the same `object_id`, `unique_id`, and state topic.
- **REQ-ACC-077** — Given a fresh startup, the five serialized retained discovery messages MUST use the device fields, IDs, and topics in REQ-HA-022. Home Assistant MUST register exactly one select per option under the shared options device. Changing the fetch schedule to `6m` through the select MUST update the runtime setting and publish `6m` to the existing retained state topic.
- **REQ-ACC-078** — Given an upgrade with all five older discovery messages retained in the broker, startup MUST replace the messages at their existing discovery topics. Home Assistant MUST discover all five selects under the options device without requiring a broker purge.
- **REQ-ACC-079** — Given an upgrade with existing select registry entries, including a user-renamed entity ID, and legacy options connection aliases on the service device, Home Assistant MUST attach all five selects to the options device after processing the corrected discovery. The existing entity IDs and original service device MUST be preserved. Repeated startup MUST produce no duplicate entities or devices. Verification MUST try an app-only restart first. If an MQTT integration reload is required and sufficient, the upgrade guidance MUST document that step.

## Runtime session recovery

- **REQ-ACC-046** — Given a working EU session, a failed runtime login sequence, and EU becoming reachable before the next permitted cycle, that cycle performs fresh authentication starting at EU, refreshes device inventory and topology, and resumes publication without a process restart. Repeated recoverable failures retain MQTT connection and values, perform fresh attempts on permitted cycles, and leave `LastRefresh` unchanged until complete synchronization succeeds.
- **REQ-ACC-047** — Given a valid persisted authentication response and failed alternative candidates, the active gateway, session, retained authentication details, remembered successful gateway/key, and valid persisted authentication/configuration remain unchanged. Forced candidates contact the login endpoint despite the existing cached token. A successful candidate is persisted and promoted; later recovery prioritizes that successful gateway/key.
- **REQ-ACC-048** — Given directly classified Docker-DNS failures during collection with no pending authentication, successive retries make fresh network attempts against the active gateway, initiate no login or rotation, preserve MQTT values, and follow the specified DNS delays. A successful sync resets outage state and resumes normal scheduling.
- **REQ-ACC-049** — Given token-invalid collection followed by recoverable forced-login failure, MQTT remains alive and retries authentication on the next permitted cycle. Given successful authentication followed by recoverable device-rediscovery failure, the next attempt retries rediscovery without another login solely for that failure. A cycle initiates at most one MQTT forced-login sequence and at most one complete collection retry; endpoint replay retains its separate existing bound.
- **REQ-ACC-050** — Given a non-recoverable authentication, persistence, rediscovery, or collection failure, the runtime returns an error rather than indefinitely retrying. Failed required persistence does not promote the candidate and obeys existing replacement-safe file rules.
- **REQ-ACC-051** — Given authentication already pending and a first-candidate Docker-DNS failure on its recovery anchor, the obligation and anchor remain intact, candidate rotation stops, and DNS backoff applies. The next permitted retry resumes authentication on that anchor; successful authentication and rediscovery allow collection to resume.

## Reliable plant PV aggregation

- **REQ-ACC-039** — Given decoded query-device API rows for two inventoried type-55 microinverters reporting `p24` values `0.8 kW` and `0.9 kW`, a complete valid topology and no native plant total, normalization and aggregation MUST yield `1.700 kW`, even without inverter names. Each device's virtual copy MUST retain its own measurement rather than sharing or overwriting the other device's value. The scenarios in `REQ-ACC-039`–`045` MUST exercise actual API decoding and normalization, not only directly constructed idealized data entries.
- **REQ-ACC-040** — Given a decoded plant-scoped `p83076` reporting `4.5 kW`, the native total MUST win over a device sum even when normalization has copied it into a virtual namespace and inventory or topology is unavailable. A raw `value` field MUST retain the enclosing point identity; raw and copied representations MUST count once. Calculated or Boolean points with a matching normalized name MUST NOT qualify as native. Conflicting source copies, recognized ID/name conflicts, and grid- or phase-specific metadata MUST reject the affected candidate; an unknown source ID MAY qualify only through an approved readable API point-name alias.
- **REQ-ACC-041** — Given nine inventoried expected producer leaves, one absent, null, invalid, or unrecognized current reading MUST NOT produce a partial plant total or remove that producer from expectation. A genuine numeric zero MUST remain a valid contributor. Incomplete AC with complete valid DC coverage MUST use DC; mixed incomplete AC/DC coverage MUST publish no new aggregate. A later successful snapshot restoring complete coverage MUST restore the aggregate without borrowing a previous-cycle value or retained MQTT state. Missing usable inventory, conflicting producer identities, unusable producer keys, and a telemetry producer absent from inventory MUST prevent a device sum.
- **REQ-ACC-042** — Given a synthetic plant containing nine type-55 microinverters each reporting `0.2 kW` AC, a plant record, an iHomeManager/controller, and grid phases reporting `+0.50`, `-0.27`, and `-0.23 kW`, the complete producer-leaf aggregate MUST be `1.800 kW`; neither the controller nor the grid phases contribute. Inverter-like diagnostics MUST count nine rather than include the plant record. The scenario MUST exercise the actual discovery/state projection and dashboard composition: the canonical plant entity belongs to the plant Home Assistant device, has unit `kW`, device class `power`, and state class `measurement`, and is preferred on a new dashboard. Existing pinned/manual sources and their compatibility migration MUST remain unchanged. Grid and phase power MUST remain ineligible for automatic PV resolution regardless of sign, unit, or plant affinity.
- **REQ-ACC-043** — Given aggregation success, suppression, endpoint filtering, unknown-parent filtering, or publication failure, each attempt MUST produce exactly one info-level final summary with the corresponding outcome, source, counts, and ordered reason from `REQ-MQTT-023`–`024`. Nine expected leaves with only eight recognized current measurements MUST report expected nine and received eight rather than success or expected eight; unavailable inventory MUST report an unknown expected count. Debug metadata MUST be sorted, bounded to 100 power-point records with an omitted count, and exclude secrets, serial numbers, raw payloads, and numeric measurement values without requiring HTTP tracing. Publication scenarios MUST exercise the actual discovery/state pipeline, and successful aggregation alone MUST NOT be reported as successful publication when filtering or publication failure follows.
- **REQ-ACC-044** — Given an expected parent producer and child producer separated by a non-producing topology node, only the child leaf MUST contribute, without double counting. A missing child reading MUST NOT enable parent fallback. A parent cycle MUST suppress device aggregation nonfatally while a valid native plant total remains eligible. Topology rejection MUST preserve other plants, ordinary entity publication, and the existing per-refresh warning limit.
- **REQ-ACC-045** — Given nine independently discovered expected producer leaves, eight producer readings plus one plant record MUST remain incomplete even when the returned row count matches `rowCount`; diagnostics MUST report expected nine and received eight. Given all nine leaves reporting valid `0.2 kW` AC measurements, decoded matching, mismatching, absent, or null `rowCount` metadata MUST NOT change the `1.800 kW` result. Given a verified native `4.5 kW` plant total and incomplete device-reading coverage, the native total MUST remain eligible. These cases MUST exercise actual API decoding, normalization, and MQTT discovery/state projection.

## Dashboard

- **REQ-ACC-012** — Given multiple type-14 devices, each gets all prototype views with unique path/title; no valid keys yields a clear error.
- **REQ-ACC-013** — Given a renamed entity with canonical registry unique ID, matching succeeds; conflicting direction/lifetime fails; multiple inverters prevent confident single-inverter production. These outcomes MUST hold through complete template generation, resolution, pruning, source mapping, and binding construction, rather than only in isolated matcher tests.
- **REQ-ACC-014** — Given no battery capability, battery cards/entities are pruned only for that target. PV-to-battery energy alone does not establish a battery.
- **REQ-ACC-015** — Given a manual override, reconciliation preserves it; if its entity disappears it remains selected/unavailable; reset restores automatic; two targets sharing a default remain isolated.
- **REQ-ACC-016** — Given direct solar above production by more than tolerance, UI requires review/confirmation. Unsupported calculated direct solar cannot be newly selected.
- **REQ-ACC-017** — Given a stale dashboard between preview and save, save aborts and local state remains unchanged. Given successful save, re-read verifies every binding before local update.
- **REQ-ACC-018** — Given locale `de-DE`, lookup uses `de`; unknown locale uses English; every supported locale has parity.
- **REQ-ACC-019** — Given source-only dashboard changes, structure hash remains stable; unrelated layout change is external modification and blocks non-forced replacement.
- **REQ-ACC-033** — Given a fresh installation, the installer stages a hashed local module, verifies its Home Assistant HTTP response and resource registration, and the three custom elements load after at most one ordinary browser reload; no data URL or CDN URL is registered.
- **REQ-ACC-034** — Given an existing working installation and a forced failure at each staging, verification, resource mutation, resource re-read, dashboard save, dashboard re-read, or state-persistence boundary, the prior resource and dashboard remain usable. Given success, exactly one canonical managed resource remains and only the active and immediately previous verified bundles are retained.
- **REQ-ACC-035** — Given a fresh installation whose asset cannot be activated, the saved dashboard uses native cards and no `custom:gosungrow-*` references. Given a later healthy reconciliation, it promotes to enhanced mode without losing targets or source-selection decisions.
- **REQ-ACC-036** — Given the pinned real Home Assistant browser fixture, opening the managed dashboard without a hard refresh loads the registered module, defines all three GoSungrow elements, and displays no configuration-error card.
- **REQ-ACC-037** — Given a Supervisor-compatible websocket proxy and authenticated `/core/info` metadata advertising port 80, 8123, or an arbitrary custom port with `ssl` false or true, installation resolves the matching `homeassistant` HTTP or HTTPS origin, verifies the staged `/local/...` asset, and succeeds with standard TLS verification. A changed advertised port is requested and used afresh on the next reconciliation. The Supervisor bearer credential is present only on the metadata request; no static request reaches `/core/local/...` or carries authorization. Given metadata HTTP 401, 403, or another non-200 response, a malformed or unsuccessful envelope, a missing or out-of-range/non-integer port, or a missing/non-boolean `ssl`, installation neither guesses nor probes an origin: it preserves an existing working dashboard or produces the native fallback on a fresh installation. Given a standalone websocket URL, verification continues to derive its corresponding HTTP origin and validate status, MIME type, and hash.
- **REQ-ACC-038** — Given Home Assistant Core started before its config-root `www` directory existed, after GoSungrow stages and hash-verifies the exact asset an HTTP 404 produces `home-assistant-static-route-unavailable`, stable class `operator_action_required`, no resource registration, an unchanged existing dashboard or native fresh-install fallback, and guidance to restart Home Assistant Core once rather than the GoSungrow app. MQTT continues and bounded reconciliation remains scheduled. After a user-controlled Core restart, reconciliation re-resolves the endpoint, verifies status, MIME type, and hash, activates the enhanced dashboard, and the browser loads all three custom elements without losing targets or source-selection decisions. HTTP 401, 403, 5xx, MIME mismatch, hash mismatch, transport failure, and Supervisor-metadata failure do not produce restart guidance.

- **REQ-ACC-052** — Given no saved selection and no eligible canonical daily source, lifetime energy MUST NOT become daily home consumption, and feed-in energy MUST NOT become solar production. These metrics remain unresolved and follow unsupported pruning without an unsafe generated default.
- **REQ-ACC-053** — Given a renamed or translated finite numeric entity with a verified target-affine canonical registry identity for `p13112` or `p13199`, complete dashboard composition MUST retain its applicable display cards, source entry, candidates, and metric-specific bindings despite no legacy entity-name match. Numeric zero remains eligible. An unrelated live-PV metric remains unaffected.
- **REQ-ACC-054** — Given globally unavailable registry metadata, canonical-looking candidates MUST NOT become confident automatic daily defaults. Given partially populated registry metadata, an entity lacking its own registry identity MUST NOT qualify through its entity ID. Wrong-target, wrong-direction, incompatible-unit, non-numeric, stale, and ambiguous candidates MUST NOT enable a legacy automatic fallback.
- **REQ-ACC-055** — Given an existing pinned daily selection, reconciliation—including forced reconciliation—preserves its identity, marks unverifiable meaning for review, withholds its unverified automatic daily presentation under REQ-SRC-029, and offers a confident safer source without adopting it silently. A previously accepted missing or temporarily stale override retains its identity under existing preservation rules even when automatic resolution finds nothing; retention does not override the presentation policy for proven incompatibility or invalid live values.
- **REQ-ACC-056** — Given multiple targets or metrics sharing entity values, canonical resolution and pruning MUST preserve separate placeholder-derived bindings and prevent cross-target rewrites. Accepting a safer recommendation follows the verified browser transaction; a matcher-version change between preview and save aborts the stale transaction.
- **REQ-ACC-057** — Given canonical success, missing eligible candidates, ambiguity, registry-verification failure, or a preserved unverified selection, debug diagnostics MUST agree with the final generated configuration and pruning outcome, obey candidate limits, and contain no credentials or tokens.

## Source verification and end-to-end availability

- **REQ-ACC-060** — Given a preserved unsupported selection ranked before eligible candidates, the selector MUST show it as the current selection needing review, never as recommended. Recommended candidates MUST be selectable, eligible, and confident; with none eligible, no recommendation MUST be fabricated. Limits MUST include the preserved selection within 20 candidates per metric and at most five recommendations. Genuine verified numeric zero MUST remain eligible.
- **REQ-ACC-061** — Given a pinned automatic daily-consumption selection with unverified meaning and numeric state `9.92 MWh`, its identity and Data Sources review entry MUST remain, but its live total, historical series, day/month/year aggregates, native-fallback value, and tooltip values MUST be withheld without inventing zero. No safer source MUST be silently adopted. The state magnitude and energy unit alone MUST NOT be reported as proof of lifetime semantics. Unrelated verified metrics MUST retain their existing values and mappings.
- **REQ-ACC-062** — Given an otherwise usable explicit manual daily selection whose meaning cannot be verified, it MUST remain displayed with persistent visible and accessible warnings wherever its current or historical values appear. Given trusted evidence proving wrong period, meaning, direction, target, or units, automatic and manual selections MUST retain their identities but withhold daily presentation. A renamed friendly name alone MUST NOT establish a conflict. A missing or invalid manual live value MUST show unavailable rather than switch source or invent zero. Existing stricter calculated-direct-solar restrictions MUST remain effective.
- **REQ-ACC-063** — Given recorder rows for a withheld source, those rows MUST NOT enter that metric's chart, tooltip, or month/year total. Given explicit adoption of a valid replacement, only the replacement's eligible history MUST be displayed, without merging or backfilling the former source's series. Withholding and replacement MUST NOT delete, rewrite, or relabel recorder data. Missing current state alone MUST NOT remove otherwise permitted completed recorder rows.
- **REQ-ACC-064** — Given a usable canonical plant-PV registry identity whose actual entity ID is renamed, translated, or suffixed, complete dashboard composition MUST resolve that actual entity, preserve the PV metric through pruning, build its source entry and bindings, and prefer it for a new unpinned dashboard. Existing pinned/manual choices retain their specified precedence. Wrong-plant identity, a conflicting registry entry, individually missing registry metadata, globally unavailable registry verification, and non-equivalent duplicate candidates MUST NOT gain confident canonical eligibility from entity-name spelling. A `_2` suffix alone MUST NOT prove duplicate equivalence or justify deletion.
- **REQ-ACC-065** — Given a canonical PV entity first becoming usable after the startup schedule has ended, availability observation MUST trigger reconciliation without restarting the app or Home Assistant. A new/unpinned dashboard MUST adopt the eligible aggregate, a pinned device source MUST receive a review recommendation, and an accepted manual choice MUST remain unchanged. The resulting actual entity ID, pruning outcome, recommendation, display decision, and metric-specific bindings MUST agree. Source-only changes MUST preserve ownership and verified-save rules; unchanged desired configuration MUST NOT be saved again even with force enabled.
- **REQ-ACC-066** — Given relevant state/registry changes in a burst, reconciliation MUST use a fixed five-second coalescing window, serialize with scheduled work, and retain at most one pending follow-up. Ordinary numeric updates without eligibility changes MUST cause no reconciliation. Transient reconciliation failures MUST retry after sequential 30/90/300-second delays and then await a new relevant transition or explicit reconciliation. Observer failures MUST reconnect at 30/90/300 seconds and then no more than once per 300 seconds, refreshing observations to recover missed transitions; unchanged observations MUST NOT cause dashboard writes. Disabled dashboard installation and main-process exit MUST cancel observation and pending work. Failures MUST preserve MQTT, manual choices, and independent API-recovery policy without forcing login solely because HA observation changed or failed.
- **REQ-ACC-067** — Given a complete compatible directional formula, the existing computed automatic node value MUST retain precedence. Removing, pruning, or invalidating any listed operand MUST prevent a partial sum from representing a total; an eligible verified direct total MUST be used instead, or unavailable when none exists. Explicit zero operands MUST remain valid. Incompatible power units MUST not yield a total. Explicit manual node selection MUST retain precedence, including an unavailable manual value without automatic substitution. A fallback battery value MUST respect the presentation sign without changing published legacy battery signs, directional status, or route suppression. These cases MUST cover wide and compact layouts.
- **REQ-ACC-068** — Given successful publisher operations but missing HA entity observation or absent dashboard bindings, diagnostics MUST distinguish those stages rather than report end-to-end success. Discovery reuse, new discovery, state completion, filtered operations, and failed operations MUST remain distinguishable. Records spanning sync and reconciliation MUST expose stable plant/measurement identities, app/matcher versions, UTC observation times, applicable stage-local identifiers, and final decisions without pretending to be an atomic snapshot or proof of browser display or arithmetic correctness. Candidate detail MUST be bounded to five per metric and normalized-point detail to 100 per plant per attempt, with deterministic order and omitted counts. Capture records MUST exclude credentials, tokens, raw payloads, serial numbers, numeric source measurement values, and JavaScript bodies without HTTP tracing.
- **REQ-ACC-069** — Given an older managed mapping configuration, reconciliation MUST migrate to matcher version 5 and validation schema 2 while retaining schema 1, existing card type, defaults, pinned defaults, and accepted override identities. Missing verification metadata MUST NOT imply verified meaning. Newly classified automatic/manual/incompatible sources MUST follow REQ-SRC-029 without changing verified working mappings. Source-policy metadata alone MUST NOT appear as an unrelated structural edit. A stale client or changed origin, verification, display decision, matcher/validation version, candidate eligibility, or binding between preview and save MUST abort mutation; live availability MUST be rechecked. Target isolation, localized warnings, and accessibility MUST remain intact.
- **REQ-ACC-070** — Given no eligible daily-consumption or grid-export source, support diagnostics MUST distinguish observed-but-rejected normalized points from invalidity, filtering, failed registry/state observation, and no source observed in the capture. They MUST expose applicable source identity, endpoint, role, unit, period, timestamp, validity, provenance, and rejection reason within bounds. A missing candidate MUST NOT be reported as proof that iSolarCloud supplies no measurement, and diagnostic gaps MUST NOT be repaired by relaxed matching, invented energy formulas, grid-phase PV inference, or changes to aggregation arithmetic. Existing aggregation, publication, and recovery behavior MUST remain unchanged.

## Runtime settings and shared source-policy format

- **REQ-ACC-071** — Given no runtime dashboard settings, standalone `mqtt run` and `mqtt sync` MUST default both enablement and replacement permission to false. Given existing app choices true or false, the app MUST pass those exact Boolean choices to `config write` and the MQTT runtime, overriding stale persisted settings. Explicit flags MUST override environment, environment MUST override persisted configuration, and persisted configuration MUST override defaults; invalid Boolean values MUST be configuration errors. Enabled false with force-update true MUST perform no automatic installation, observation, scheduled reconciliation, or availability-driven reconciliation. A Supervisor token or existing dashboard MUST NOT enable runtime work implicitly. Explicit `ha install-dashboard` MUST remain independently available. Missing dashboard prerequisites with runtime work enabled MUST produce an actionable dashboard failure while MQTT remains operational, without adding app options or bypassing existing ownership rules.
- **REQ-ACC-072** — Given generated mapping metrics and display-card `source_policy` records, their `mapping_id`, canonical metric keys, `entity_id`, `selection_origin`, `verification`, `display_decision`, and `reason` MUST agree with the effective selection and applicable bindings for each target. Renamed actual entity IDs and genuine numeric zero MUST remain supported; an absent source MUST retain empty `entity_id` rather than imply zero. Live availability and freshness MUST be evaluated separately from current HA state. Missing, malformed, wrong-target, or identity-mismatched policy MUST NOT grant verified meaning or source-save permission; presentation MUST follow REQ-SRC-028–031 and mutation MUST wait for refreshed valid metadata. No policy record MUST contain numeric measurements, credentials, or raw payloads.
- **REQ-ACC-073** — Given source selection, reset, or recommendation adoption, a successful browser transaction MUST update and verify every affected source-policy record together with the effective selection and entity bindings. Changed or invalid policy between preview and save MUST abort mutation. A failed or stale save MUST leave the prior configuration and local UI state unchanged; successful save MUST re-read and verify policy as well as bindings before local success. Shared entity values across metrics or targets MUST NOT cause cross-metric or cross-target policy updates.
- **REQ-ACC-074** — Given enhanced-to-native fallback, each native Data Sources notice MUST retain the target's `gosungrow_source_mapping` identity, versions, defaults, pinned defaults, accepted overrides, and metric policy records without transient candidates or obsolete binding paths. Given later promotion, those source identities MUST survive while fresh observations rebuild verification, candidates, display decisions, and binding paths. Retained policy MUST NOT imply current eligibility, and reset/current-config precedence MUST remain intact. Source-policy-only metadata changes MUST NOT count as unrelated structural modification, while unrelated layout edits remain protected. The round-trip MUST continue applying display safety without custom native cards, a new state file or service, recorder mutation, or cross-target leakage.

- **REQ-ACC-075** — Given a native tile or a native graph containing one withheld daily metric and another permitted metric, the affected card MUST retain valid paired `source_policy.native_template` and `source_policy.native_bindings` metadata under REQ-SRC-032. For the transition withheld → verified → withheld, only the affected metric's numeric presentation MUST disappear, restore, and disappear again; other permitted series, non-source properties, layout, and saved selection identities MUST remain intact. Explicit adoption of a verified replacement MUST rebind the template's owned entity paths and regenerate final rendered binding paths in the same verified transaction as the policy and selection update, without resurrecting the old source or treating missing data as zero. Source-only projection changes MUST preserve structure ownership, while unrelated edits to either the retained template or rendered layout remain detectable. Missing-pair, stale, identity-mismatched, unresolved, cross-card/cross-target, or multiply owned path metadata MUST abort mutation rather than guess a layout; failed saves MUST leave the prior saved configuration and local UI state unchanged. Distinct metrics sharing an entity ID MUST retain distinct path ownership. Capture of a template MUST not include live measurements, credentials, raw payloads, recursive templates, or hidden-card storage, and the transition MUST not add entities or mutate recorder history.

A manually selected battery value MUST remain unchanged; a differing value MUST prevent duplicate-label suppression. An unavailable battery node MUST not suppress an active wide-layout route label. ## Configuration and source-of-truth workflow

- **REQ-ACC-025** — Given `GOSUNGROW_TIMESTAMP_OFFSET_MS=" 1500 "`, a request timestamp advances by 1500 milliseconds after the learned server offset; given an absent, empty, or invalid value, it advances by zero diagnostic milliseconds.
- **REQ-ACC-026** — Given an approved plan packet followed by `do this`, spec and derived implementation changes are made on one feature branch for one pull request; given base-commit, fingerprint, scope, or overlapping-worktree drift, no plan-dependent write occurs until renewed approval.
- **REQ-ACC-027** — Given a new tracked product file or repository-owned environment lookup, validation fails until the source inventory or configuration catalog classifies it.

## Failure diagnostics

- **REQ-ACC-028** — Given a stable recoverable-remote classification whose human-readable diagnostic contains Docker-DNS text, the app wrapper uses normal remote recovery; given a stable Docker-DNS classification whose text does not contain resolver keywords, it uses DNS backoff. Human-readable wording alone never selects recovery.
- **REQ-ACC-029** — Given a failed multi-candidate login sequence, diagnostics list hosts in attempt order, identify the first failure and terminal stop reason, retain at most two distinct messages per host, and contain no user credentials or session tokens.

## Prohibited behavior

An acceptance test MUST NOT weaken its governing subsystem requirement. When an example and a subsystem requirement appear inconsistent, the more specific safety constraint wins and the inconsistency must be corrected.

Acceptance behavior MUST NOT log JavaScript bundle contents, store custom-card references before activation succeeds, delete the last verified working bundle, mutate unrelated Lovelace resources, require HACS or a CDN, restart Home Assistant automatically, or require a Home Assistant restart outside the explicit `/local` bootstrap exception in `REQ-DASH-037`.
