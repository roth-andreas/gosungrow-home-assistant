# Acceptance scenarios

Status: Normative  
Scope: Cross-subsystem executable examples

## Authentication and transport

- **REQ-ACC-001** — Given a missing token file, login proceeds to the network without a file error; given corrupt token JSON, the file is removed and login proceeds.
- **REQ-ACC-002** — Given configured host/key rejection, login tries unique candidates in specified order. The Indian gateway occurs exactly once in automatic rotation; when configured explicitly it is first, while the existing gateways retain their relative order. Given `127.0.0.11:53` on the first candidate, rotation stops and returns for DNS backoff. Given an earlier authentication/gateway failure followed by `127.0.0.11:53` on a later candidate, rotation stops, preserves both failures, and remains classified as a recoverable remote login sequence rather than a general Docker-DNS outage.
- **REQ-ACC-003** — Given a timed-out HTTP request, a later request can succeed because requests use a bounded private client rather than corrupting the global client.
- **REQ-ACC-004** — Given a common request with a token, debug string contains `<redacted>` and not the token.

## Data

- **REQ-ACC-005** — Numeric and composite plant IDs round-trip; `NULL`, `--`, and invalid composite placeholders do not become zero.
- **REQ-ACC-006** — Given kVAr/MVAr/mVAr variants, reactive power publishes equivalent `var` values and `reactive_power` metadata; applying normalization twice changes nothing.
- **REQ-ACC-007** — Given any missing operand in a virtual formula, dependent virtual points are absent while independent virtual points remain.
- **REQ-ACC-008** — Given a plant-local timestamp, its wall-clock components remain and correct zone offset is attached; invalid timezone retains the original.

## MQTT and Home Assistant

- **REQ-ACC-009** — Given one plant with types 14, 11, and 22, realtime selects type 14; without 14 it selects 11; each additional plant gets its own batch.
- **REQ-ACC-010** — Given Docker DNS loss after connection, MQTT remains connected and delays follow 15/30/60/120/300 seconds; success restores five minutes.
- **REQ-ACC-011** — Given textual, numeric instant, numeric daily, and reactive-power values, discovery respectively has no measurement metadata, measurement, total/last-reset, and canonical reactive metadata.
- **REQ-ACC-030** — Given a numeric `Wp` value, normalization and discovery publish the scaled value in `kWp` with frequency-derived state metadata and `mdi:lightning-bolt`, but without `device_class`; given an otherwise equivalent `kW` value, discovery continues to publish device class `power`.
- **REQ-ACC-031** — Given two producer leaves reporting `1.2 kW` and `800 W` DC with no native total or complete AC tier, the plant publishes `2.000 kW` at `sensor.gosungrow_virtual_<ps_id>_pv_power`. A valid native plant total wins without adding device values; complete AC coverage wins over DC coverage; topology excludes a parent when its children contribute. Mixed incomplete AC/DC coverage, a missing expected contributor, an invalid value, or an incompatible unit produces no new aggregate. A new dashboard selects the plant entity, an existing pinned or manual source is not silently rewritten, and without an aggregate multiple producers cannot resolve to one automatic plant total.
- **REQ-ACC-032** — Given plant-tree UUID/UpUUID relationships and expected producers established independently from current numeric values, producer leaves are resolved within their opaque plant ID, including relationships through intermediate non-producing nodes. Duplicate UUIDs, dangling or cross-plant parent references, parent cycles, and unavailable topology suppress device aggregation without stopping MQTT; a native plant total still publishes. Successful token recovery refreshes device inventory, discovered point metadata, and plant topology; unsuccessful rediscovery does not redefine expected producer membership.

## Runtime session recovery

- **REQ-ACC-046** — Given a working EU session, a failed runtime login sequence, and EU becoming reachable before the next permitted cycle, that cycle performs fresh authentication starting at EU, refreshes device inventory and topology, and resumes publication without a process restart. Repeated recoverable failures retain MQTT connection and values, perform fresh attempts on permitted cycles, and leave `LastRefresh` unchanged until complete synchronization succeeds.
- **REQ-ACC-047** — Given a valid persisted authentication response and failed alternative candidates, the active gateway, session, retained authentication details, remembered successful gateway/key, and valid persisted authentication/configuration remain unchanged. Forced candidates contact the login endpoint despite the existing cached token. A successful candidate is persisted and promoted; later recovery prioritizes that successful gateway/key.
- **REQ-ACC-048** — Given directly classified Docker-DNS failures during collection with no pending authentication, successive retries make fresh network attempts against the active gateway, initiate no login or rotation, preserve MQTT values, and follow the specified DNS delays. A successful sync resets outage state and resumes normal scheduling.
- **REQ-ACC-049** — Given token-invalid collection followed by recoverable forced-login failure, MQTT remains alive and retries authentication on the next permitted cycle. Given successful authentication followed by recoverable device-rediscovery failure, the next attempt retries rediscovery without another login solely for that failure. A cycle initiates at most one MQTT forced-login sequence and at most one complete collection retry; endpoint replay retains its separate existing bound.
- **REQ-ACC-050** — Given a non-recoverable authentication, persistence, rediscovery, or collection failure, the runtime returns an error rather than indefinitely retrying. Failed required persistence does not promote the candidate and obeys existing replacement-safe file rules.
- **REQ-ACC-051** — Given authentication already pending and a first-candidate Docker-DNS failure on its recovery anchor, the obligation and anchor remain intact, candidate rotation stops, and DNS backoff applies. The next permitted retry resumes authentication on that anchor; successful authentication and rediscovery allow collection to resume.

## Reliable plant PV aggregation

- **REQ-ACC-039** — Given decoded query-device API rows for two inventoried type-55 microinverters reporting `p24` values `0.8 kW` and `0.9 kW`, a complete valid topology and no native plant total, normalization and aggregation MUST yield `1.700 kW`, even without inverter names. Each device's virtual copy MUST retain its own measurement rather than sharing or overwriting the other device's value. The scenarios in `REQ-ACC-039`–`045` MUST exercise actual API decoding and normalization, not only directly constructed idealized data entries.
- **REQ-ACC-040** — Given a decoded plant-scoped `p83076` reporting `4.5 kW`, the native total MUST win over a device sum even when normalization has copied it into a virtual namespace and inventory or topology is unavailable. A raw `value` field MUST retain the enclosing point identity; raw and copied representations MUST count once. Calculated or Boolean points with a matching normalized name MUST NOT qualify as native. Conflicting source copies, recognized ID/name conflicts, and grid- or phase-specific metadata MUST reject the affected candidate; an unknown source ID MAY qualify only through an approved readable API point-name alias.
- **REQ-ACC-041** — Given nine inventoried expected producer leaves, one absent, null, invalid, or unrecognized current reading MUST NOT produce a partial plant total or remove that producer from expectation. A genuine numeric zero MUST remain a valid contributor. Incomplete AC with complete valid DC coverage MUST use DC; mixed incomplete AC/DC coverage MUST publish no new aggregate. A later successful snapshot restoring complete coverage MUST restore the aggregate without borrowing a previous-cycle value or retained MQTT state. Missing usable inventory, conflicting producer identities, unusable producer keys, and a telemetry producer absent from inventory MUST prevent a device sum.
- **REQ-ACC-042** — Given a synthetic plant containing nine type-55 microinverters each reporting `0.2 kW` AC, a plant record, an iHomeManager/controller, and grid phases reporting `+0.50`, `-0.27`, and `-0.23 kW`, the complete producer-leaf aggregate MUST be `1.800 kW`; neither the controller nor the grid phases contribute. Inverter-like diagnostics MUST count nine rather than include the plant record. The scenario MUST exercise the actual discovery/state projection and dashboard composition: the canonical plant entity belongs to the plant Home Assistant device, has unit `kW`, device class `power`, and state class `measurement`, and is preferred on a new dashboard. Existing pinned/manual sources and their compatibility migration MUST remain unchanged. Grid and phase power MUST remain ineligible for automatic PV resolution regardless of sign, unit, or plant affinity.
- **REQ-ACC-043** — Given aggregation success, suppression, endpoint filtering, unknown-parent filtering, or publication failure, each attempt MUST produce exactly one info-level final summary with the corresponding outcome, source, counts, and ordered reason from `REQ-MQTT-023`–`024`. Nine expected leaves with only eight recognized current measurements MUST report expected nine and received eight rather than success or expected eight; unavailable inventory MUST report an unknown expected count. Debug metadata MUST be sorted, bounded to 100 power-point records with an omitted count, and exclude secrets, serial numbers, raw payloads, and numeric measurement values without requiring HTTP tracing. Publication scenarios MUST exercise the actual discovery/state pipeline, and successful aggregation alone MUST NOT be reported as successful publication when filtering or publication failure follows.
- **REQ-ACC-044** — Given an expected parent producer and child producer separated by a non-producing topology node, only the child leaf MUST contribute, without double counting. A missing child reading MUST NOT enable parent fallback. A parent cycle MUST suppress device aggregation nonfatally while a valid native plant total remains eligible. Topology rejection MUST preserve other plants, ordinary entity publication, and the existing per-refresh warning limit.
- **REQ-ACC-045** — Given nine independently discovered expected producer leaves, eight producer readings plus one plant record MUST remain incomplete even when the returned row count matches `rowCount`; diagnostics MUST report expected nine and received eight. Given all nine leaves reporting valid `0.2 kW` AC measurements, decoded matching, mismatching, absent, or null `rowCount` metadata MUST NOT change the `1.800 kW` result. Given a verified native `4.5 kW` plant total and incomplete device-reading coverage, the native total MUST remain eligible. These cases MUST exercise actual API decoding, normalization, and MQTT discovery/state projection.

## Dashboard

- **REQ-ACC-012** — Given multiple type-14 devices, each gets all prototype views with unique path/title; no valid keys yields a clear error.
- **REQ-ACC-013** — Given a renamed entity with canonical registry unique ID, matching succeeds; conflicting direction/lifetime fails; multiple inverters prevent confident single-inverter production.
- **REQ-ACC-014** — Given no battery capability, battery cards/entities are pruned only for that target. PV-to-battery energy alone does not establish a battery.
- **REQ-ACC-015** — Given a manual override, reconciliation preserves it; if its entity disappears it remains selected/unavailable; reset restores automatic; two targets sharing a default remain isolated.
- **REQ-ACC-016** — Given direct solar above production by more than tolerance, UI requires review/confirmation. Unsupported calculated direct solar cannot be newly selected.
- **REQ-ACC-017** — Given a stale dashboard between preview and save, save aborts and local state remains unchanged. Given successful save, re-read verifies every binding before local update.
- **REQ-ACC-018** — Given locale `de-DE`, lookup uses `de`; unknown locale uses English; every supported locale has parity.
- **REQ-ACC-019** — Given source-only dashboard changes, structure hash remains stable; unrelated layout change is external modification and blocks non-forced replacement.
- **REQ-ACC-033** — Given a fresh installation, the installer stages a hashed local module, verifies its Home Assistant HTTP response and resource registration, and the three custom elements load after at most one ordinary browser reload; no data URL or CDN URL is registered.
- **REQ-ACC-034** — Given an existing working installation and a forced failure at each staging, verification, resource mutation, resource re-read, dashboard save, dashboard re-read, or state-persistence boundary, the prior resource and dashboard remain usable. Given success, exactly one canonical managed resource remains and only the active and immediately previous verified bundles are retained.
- **REQ-ACC-035** — Given a fresh installation whose asset cannot be activated, the saved dashboard uses native cards and no `custom:gosungrow-*` references. Given a later healthy reconciliation, it promotes to enhanced mode without losing targets or source-selection decisions.
- **REQ-ACC-036** — Given the pinned real Home Assistant browser fixture, opening the managed dashboard without a hard refresh loads the registered module, defines all three GoSungrow elements, and displays no configuration-error card.
- **REQ-ACC-037** — Given a Supervisor-compatible websocket proxy and authenticated `/core/info` metadata advertising port 80, 8123, or an arbitrary custom port with `ssl` false or true, installation resolves the matching `homeassistant` HTTP or HTTPS origin, verifies the staged `/local/...` asset, and succeeds with standard TLS verification. A changed advertised port is requested and used afresh on the next reconciliation. The Supervisor bearer credential is present only on the metadata request; no static request reaches `/core/local/...` or carries authorization. Given metadata HTTP 401, 403, or another non-200 response, a malformed or unsuccessful envelope, a missing or out-of-range/non-integer port, or a missing/non-boolean `ssl`, installation neither guesses nor probes an origin: it preserves an existing working dashboard or produces the native fallback on a fresh installation. Given a standalone websocket URL, verification continues to derive its corresponding HTTP origin and validate status, MIME type, and hash.
- **REQ-ACC-038** — Given Home Assistant Core started before its config-root `www` directory existed, after GoSungrow stages and hash-verifies the exact asset an HTTP 404 produces `home-assistant-static-route-unavailable`, stable class `operator_action_required`, no resource registration, an unchanged existing dashboard or native fresh-install fallback, and guidance to restart Home Assistant Core once rather than the GoSungrow app. MQTT continues and bounded reconciliation remains scheduled. After a user-controlled Core restart, reconciliation re-resolves the endpoint, verifies status, MIME type, and hash, activates the enhanced dashboard, and the browser loads all three custom elements without losing targets or source-selection decisions. HTTP 401, 403, 5xx, MIME mismatch, hash mismatch, transport failure, and Supervisor-metadata failure do not produce restart guidance.

## Frontend summaries

- **REQ-ACC-020** — Fresh install with only live daily value displays one bucket for day/month/year. Current-day recorder rows are replaced, not added.
- **REQ-ACC-021** — Month/year boundaries keep completed previous period totals and start current period from live day. Missing data yields empty chart.
- **REQ-ACC-022** — Date labels follow Home Assistant preferences, relabel cached data without refetch, and expose matching keyboard/tooltip labels.

## Add-on and release

- **REQ-ACC-023** — Dashboard failure logs warning and MQTT starts; missing credentials or MQTT host is fatal; panic output exits without login refresh. Missing or empty `gosungrow_host` uses the existing Australian default, selecting `https://gateway.isolarcloud.in` persists and uses it as the configured gateway, and an unsupported gateway fails before dashboard or MQTT startup.
- **REQ-ACC-024** — Binary and app versions align, specs pass consistency validation, Go tests pass, shell parses, and amd64 image builds before publication.

## Configuration and source-of-truth workflow

- **REQ-ACC-025** — Given `GOSUNGROW_TIMESTAMP_OFFSET_MS=" 1500 "`, a request timestamp advances by 1500 milliseconds after the learned server offset; given an absent, empty, or invalid value, it advances by zero diagnostic milliseconds.
- **REQ-ACC-026** — Given an approved plan packet followed by `do this`, spec and derived implementation changes are made on one feature branch for one pull request; given base-commit, fingerprint, scope, or overlapping-worktree drift, no plan-dependent write occurs until renewed approval.
- **REQ-ACC-027** — Given a new tracked product file or repository-owned environment lookup, validation fails until the source inventory or configuration catalog classifies it.

## Failure diagnostics

- **REQ-ACC-028** — Given a stable recoverable-remote classification whose human-readable diagnostic contains Docker-DNS text, the app wrapper uses normal remote recovery; given a stable Docker-DNS classification whose text does not contain resolver keywords, it uses DNS backoff. Human-readable wording alone never selects recovery.
- **REQ-ACC-029** — Given a failed multi-candidate login sequence, diagnostics list hosts in attempt order, identify the first failure and terminal stop reason, retain at most two distinct messages per host, and contain no user credentials or session tokens.

## Prohibited behavior

An acceptance test MUST NOT weaken its governing subsystem requirement. When an example and a subsystem requirement appear inconsistent, the more specific safety constraint wins and the inconsistency must be corrected.

Acceptance behavior MUST NOT log JavaScript bundle contents, store custom-card references before activation succeeds, delete the last verified working bundle, mutate unrelated Lovelace resources, require HACS or a CDN, restart Home Assistant automatically, or require a Home Assistant restart outside the explicit `/local` bootstrap exception in `REQ-DASH-037`.
